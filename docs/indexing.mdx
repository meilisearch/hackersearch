## Data source

The [official HN Firebase API](https://github.com/HackerNews/API) exposes every
item ever created under sequential ids (`/v0/item/{id}.json`), the current
`/v0/maxitem.json`, and recently changed ids under `/v0/updates.json`.

## Commands

```sh
hn-indexer settings                # create both indexes + apply settings
hn-indexer backfill [--recent N]   # maxitem → 1, or only the last N ids
hn-indexer backfill --since-days N # everything posted in the last N days
hn-indexer sync [--interval 30]    # follow new + updated items forever
hn-indexer run [--recent N]        # settings + backfill + sync in one process
hn-indexer split                   # one-time: migrate the pre-split `hn` index
```

`--since-days` binary-searches the sequential id space for the item closest to
the requested cutoff, then backfills from `maxitem` down to it.

The backfill walks ids downward in chunks (default 2000 ids, 128 concurrent
requests) and checkpoints progress to `indexer-state.json` after every chunk,
so it can be interrupted and resumed at any time. Expect ~750 ids/s, which puts
the full corpus at roughly 17 hours.

## Document schema

```json
{
  "id": 44251337,
  "type": "story",
  "tags": ["story", "show_hn"],
  "title": "Show HN: ...",
  "text": "Plain text: paragraphs as blank lines, links as their full href",
  "url": "https://example.com/post",
  "domain": "example.com",
  "author": "pg",
  "points": 128,
  "num_comments": 42,
  "created_at": 1751896800,
  "parent": null
}
```

Deleted and dead items are skipped. `tags` powers the type facet and adds
`ask_hn` / `show_hn` / `launch_hn` / `tell_hn` derived from title prefixes,
mirroring the tag scheme HN Search users know.

## Article enrichment (embeddings)

`hn-indexer enrich` implements the [hackerverse](https://github.com/wilsonzlin/hackerverse)
idea: fetch the page each story links to, strip non-primary HTML5 elements,
and keep the main text (default 4,000 chars, `ENRICH_MAX_CHARS`). With
`CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_API_TOKEN` set (or `--extractor
cloudflare`), pages are instead rendered in Cloudflare Browser Rendering's
headless browser and returned as markdown — JS-heavy sites included — with
the local extractor as automatic per-page fallback. The result
is stored as `content` on the document plus an `enriched: true` marker so
attempts (including failures) are never repeated. `content` is **not** a
searchable attribute — it only feeds the embedder's document template:

```
{{ doc.type }}: {{ doc.title }} + content (or the item's own text for comments)
```

Enable an embedder afterwards with `settings --embedder huggingface` (local,
keyless) or `--embedder openai` (needs `OPENAI_API_KEY`). Document upserts use
HTTP `PUT` (add-or-update), so re-syncing an item never erases its enrichment.

## Indexes and settings

Every item is routed by its `type`: comments go to `hn-comments`, everything
else (stories, jobs, polls, poll options) to `hn-stories`. The UI's two tabs
map one-to-one onto them.

**`hn-stories`**

- **searchableAttributes**: `title`, `text`
- **filterableAttributes**: `type`, `tags`, `url`, `author`, `domain`, `points`, `num_comments`, `created_at`, `enrich_gen`
- **sortableAttributes**: `created_at`, `points`, `num_comments`
- **rankingRules**: `words`, `typo`, `proximity`, `sort`, `attributeRank`,
  `points:desc`, `wordPosition`, `exactness`. Points sit before word position
  and exactness, so among equally good matches the story HN upvoted wins over
  its low-point reposts, and an empty query is a "top of HN" view
- **dictionary**: `C++`, `C#`, `F#` stay whole terms instead of searching as "c"

**`hn-comments`** — only what the Comments tab and thread view query

- **searchableAttributes**: `text`
- **filterableAttributes**: `author`, `parent`, `created_at`
- **sortableAttributes**: `created_at`
- **rankingRules**: the stories rules minus `points:desc` — HN has no comment scores
- **embedders**: none — comments are never embedded

## Changing settings on a live index

`hn-indexer settings` pushes the whole definition, which reindexes a populated
index. Two narrow commands exist for production:

```sh
hn-indexer ranking                # ranking rules only — applied at search time, no reindex
hn-indexer dictionary stories     # tokenizer dictionary — reindexes hn-stories
hn-indexer dictionary comments    # …and hn-comments (~40M documents: hours)
```

## Migrating from the single `hn` index

Before the split everything lived in one `hn` index. While it exists, every
command except `split` refuses to run. Stop the old indexer, then:

```sh
hn-indexer split
```

It configures `hn-stories`, copies every non-comment document into it (whole,
so enrichment is kept), verifies the count, deletes those documents from
`hn`, renames `hn` to `hn-comments` in place, and submits the comment
settings as a background task. It is checkpointed and safe to re-run.
Vectors are not copied: re-run `hn-indexer embedder` afterwards if `hn` had
one.
