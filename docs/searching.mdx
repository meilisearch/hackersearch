---
title: Searching
description: How the web UI queries Meilisearch.
---

## One round-trip per keystroke

Each tab searches its own index — News queries `hn-stories`, Comments
queries `hn-comments` — so a query only ever touches the corpus it can show.
The UI issues a single [`/multi-search`](https://www.meilisearch.com/docs/reference/api/multi_search)
request containing:

1. the **main query** — paginated, highlighted, cropped;
2. one **facet-count query per dimension** (`tags`, `domain`, `author`), each
   with that dimension's own filter removed and `limit: 0`.

This yields *disjunctive* facet counts: checking "Show HN" doesn't zero out the
"Ask HN" count, so facets behave the way users expect from HN Search.

## The cached front page

The search every visitor lands on — no query, no filters, News tab — ranks
all ~5M stories by points and counts facets over all of them: 0.7–0.9 s of
engine time, identical for everyone. It is served from `/api/front-page`
instead, a route the CDN caches for a minute (`s-maxage=60`,
`stale-while-revalidate`). If that route fails, the UI searches Meilisearch
directly, so the cache can only make the front page faster.

## Pagination

Both indexes cap `pagination.maxTotalHits` at 10,000, so the pager stops at
page 500 even when more documents match. A link past that shows a notice
rather than an empty page.

## Story context on comments

Comments only carry `parent`, so each comment hit's story is found by
climbing the reply chain — for the whole page at once. Each round fetches
every still-unknown ancestor in one `POST /documents/fetch` per index, so a
page costs as many round-trips as its deepest comment, and cards show their
"on: <story>" line as soon as their own chain resolves. Ancestors are cached
for the session.

## Filters

Selections within a facet are ORed, facets are ANDed:

```
[["tags = story", "tags = show_hn"], ["domain = github.com"], "points >= 100", "created_at >= 1719000000"]
```

## Safe highlighting

Highlight markers are Unicode private-use-area characters (``/``)
rather than HTML tags. The React app splits on them and renders `<mark>`
elements itself — no `dangerouslySetInnerHTML`, no XSS surface, even though the
indexed corpus is user-generated content.

## URL state

Every piece of search state (`q`, `tags`, `domains`, `authors`, `date`,
`points`, `sort`, `page`) round-trips through the query string, so any search
is a shareable, bookmarkable link. Press <kbd>/</kbd> to focus the search box.
